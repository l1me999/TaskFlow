# Архитектура TaskFlow

## Цель

Личный трекер задач и дедлайнов по проектам. Один пользователь, Windows + Android,
данные принадлежат пользователю и лежат на устройстве.

Текущий этап — **MVP без синхронизации**. Схема данных и хранилище при этом
проектируются так, чтобы синхронизацию можно было добавить без переделки модели.

## Модули

```text
shared/  (KMP: android + desktop)
├─ commonMain
│  ├─ model/    Project, Task, TaskFlowData, TaskScope, запросы и сортировка
│  ├─ data/     TaskStore — единственный владелец состояния и файла
│  ├─ platform/ expect-функции: nowMillis(), todayIsoDate(), конвертация дат
│  └─ ui/       App, Sidebar, TaskList, TaskCheckbox, QuickAddBar, TaskDetails, Dialogs, Theme, Icons
├─ androidMain   actual-реализации на java.time
├─ desktopMain   actual-реализации на java.time
└─ commonTest    тесты запросов, сортировки, хранилища и дефолтов быстрого ввода
```

`androidApp` и `desktopApp` — тонкие оболочки. Они решают только две задачи:
создать `TaskStore` с правильным путём и показать `App(store)`.

## Модель данных

```kotlin
Project(id, name, colorHex)
Task(id, title, projectId?, notes, dueDate?, important, repeatRule, done, createdAt, updatedAt)
TaskFlowData(schemaVersion, projects, tasks)   // schemaVersion = 3
```

- `dueDate` — ISO-строка `YYYY-MM-DD` или `null`. Строковое сравнение корректно
  упорядочивает даты и позволяет проверять просрочку без библиотеки дат.
- `important` — флаг «звёздочки» для списка «Важно». Появился в `schemaVersion 2`;
  старые файлы читаются без миграции, отсутствующее поле считается `false`.
- `repeatRule` — правило повтора (`None`, `Daily`, `Weekdays`, `Weekly`,
  `Monthly`, `Yearly`), появилось в `schemaVersion 3`. Без `dueDate` не имеет
  смысла и при сохранении сбрасывается в `None`.
- `updatedAt` и `createdAt` — epoch millis. Нужны для сортировки и будущего sync.
- `id` — `<prefix>-<millis>-<random>`. Уникален на устройстве; при появлении
  синхронизации будет заменён на UUID (см. ниже).


## Хранилище

Единственный источник истины — `TaskStore`:

1. При старте читает JSON (или возвращает пустую модель, если файла нет).
2. При каждом изменении обновляет `mutableStateOf` — Compose перерисовывается сам.
3. Пишет документ в `taskflow.json.tmp`, затем атомарно заменяет `taskflow.json`.

Если файл повреждён, он копируется в `taskflow.json.corrupt-<millis>`, приложение
стартует с пустыми данными и не теряет исходник.

Ограничения MVP, зафиксированные сознательно:

- запись синхронная, в UI-потоке (документ маленький);
- нет истории изменений и отмены;
- нет блокировок между процессами.

## Списки, сортировка и сроки

Разделы навигации описаны двумя типами:

- `TaskScope` (модель) — какие задачи попадают в список;
- `TaskView` (UI) — что именно открыто, включая конкретный проект и экран
  списка проектов.

| Раздел | Что попадает |
| --- | --- |
| Сегодня | незакрытые задачи со сроком `<= today` (просроченные тоже) |
| Важно | незакрытые задачи с `important = true` |
| Планируемое | незакрытые задачи с любым сроком |
| Все задачи | все незакрытые задачи |
| Проект | незакрытые задачи выбранного проекта |

Сортировка: в списках по датам — ближайший срок, затем важные, затем новые;
в смешанных списках — важные, затем задачи со сроком, затем остальные.
`isOverdue(today)` — срок в прошлом, задача не закрыта. Выполненные задачи
не исчезают из списка: они собраны в блок «Выполненные» внизу, который раскрыт
по умолчанию (заголовок с количеством сворачивает его вручную).

## Быстрый ввод

Задача создаётся одной строкой внизу: название, Enter или стрелка. Дата,
важность и проект задаются потом в деталях. Раздел влияет на дефолты:

- «Сегодня» и «Планируемое» подставляют срок = сегодня;
- «Важно» подставляет флаг «важно».

Иначе задача исчезла бы из текущего списка сразу после добавления.

## Повторяющиеся задачи

Правило повтора задаётся в деталях задачи (`Повтор`) и работает только вместе
со сроком: без даты вариант «Повтор» заблокирован, а при очистке даты правило
сбрасывается в `None`.

Отметка «выполнено» у повторяющейся задачи:

1. закрывает текущее вхождение (оно остаётся в «Выполненных» как история);
2. создаёт новую открытую задачу с тем же названием, заметками, проектом,
   звёздочкой и правилом;
3. ставит ей следующий срок — не раньше сегодняшнего дня, чтобы вернувшаяся
   из отпуска ежедневная задача не оказалась сразу просроченной.

Следующая дата считается в `commonMain` (`model/Repeat.kt`, `model/DateMath.kt`):
`java.time` недоступен, поэтому используется алгоритм «дней с 1970-01-01».
Особенности: «по будням» перепрыгивает субботу и воскресенье, месячный повтор
прижимает 31-е к последнему дню короткого месяца, годовой — 29 февраля
к 28-му. Снятие отметки «выполнено» ничего не создаёт и не удаляет.

## UI и адаптивность

`TaskFlowApp` строит один из двух макетов по ширине окна (`BoxWithConstraints`,
порог 840dp):

- Windows — сайдбар с разделами и счётчиками + широкая колонка задач, детали
  открываются справа;
- Android — одна колонка, навигация в нижней панели, детали открываются
  на весь экран.

Тема — Material 3, светлая или тёмная по системной настройке.

Фон можно заменить своим изображением (пока только Windows): кнопка «Фон»
внизу сайдбара открывает системный диалог, а выбранный файл копируется в
`background.img` рядом с `taskflow.json`. Копия важна: перенос или удаление
исходного файла не должно ломать оформление. Файл декодируется один раз при
запуске; битый или несуществующий просто игнорируется.

Когда фото выбрано, тема принудительно тёмная (светлый текст поверх затемнённого
снимка читается, тёмный — нет), картинка приглушается, панели становятся
полупрозрачными (`chromeColor` в `Theme.kt`), а верх экрана получает
дополнительную тень под заголовок: у него нет своей панели. Без фото всё
как раньше — плоский фон и непрозрачные панели.

Корневой `Surface` прозрачный: он задаёт только `LocalContentColor`, без него
текст вне `Surface` остался бы чёрным на тёмном фоне.

Чекбокс задачи — свой (`TaskCheckbox.kt`): ровный круг, при выполнении
заливается зелёным и показывает белую галочку. Material-`Checkbox` при
растягивании превращается в овал, поэтому он не подошёл.

Детали задачи сохраняются при закрытии: крестик в заголовке, `Esc` и кнопка
«Готово» делают одно и то же. Отдельной кнопки «Отмена» нет — она позволяла
молча потерять введённый текст. Пустое название не сохраняется, остаётся
прежнее.

## Платформенные различия

| Что | Windows | Android |
| --- | --- | --- |
| Каталог данных | `%USERPROFILE%\.taskflow` | `filesDir` |
| Время и дата | `java.time` | `java.time` (minSdk 26) |
| compileSdk | — | 37 (требование Compose 1.12) |

Java-код находится только в `androidMain`/`desktopMain`, поэтому `commonMain`
остаётся переносимым (пригодится для iOS, если появится).

## Дорожная карта синхронизации

Когда пользователь попросит:

1. Заменить самодельные id на UUID.
2. Добавить `deletedAt` (tombstones) вместо физического удаления.
3. Ввести понятие `deviceId` и `serverRevision`.
4. Синхронизировать по `updatedAt`, разрешая конфликты «последняя запись побеждает»
   с ручным разрешением при одновременном изменении.
5. Только после этого — сетевой слой (Supabase: Postgres + Auth + RLS, SDK `supabase-kt`).

До этого момента никакие сетевые зависимости не добавляются.

## Принятые решения

| Решение | Причина |
| --- | --- |
| KMP + Compose Multiplatform | Один язык и UI на обе платформы, нативный Compose на Android, рост в Kotlin |
| JSON вместо SQLite | Данных мало, схема ещё меняется, меньше зависимостей на старте |
| Compose в `shared` | UI пишется один раз; оболочки платформ остаются тонкими |
| Без синхронизации в MVP | Сначала рабочее локальное приложение, потом обмен данными |
| UI в духе Microsoft To Do | Привычная однострочная запись задачи и умные списки вместо диалога создания |
| Собственный набор иконок на Canvas (`Icons.kt`) | `material-icons-extended` не кэширован, сборка идёт офлайн; Canvas-пути масштабируются, красятся темой и одинаковы на Windows и Android |
